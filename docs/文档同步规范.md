# 文档同步规范

本文档不是项目内容文档，而是“把项目进展同步到 `docs/` 时的操作规范”。

目标只有两个：

1. 让不同 AI 在同步文档时写到正确的位置
2. 避免同一条进展被重复写进多个文档，或者写成难以维护的流水账

如果你这次的任务包含“更新文档 / 同步进展 / 持久化当前状态”，请先读本文档，再动手修改 `docs/`。

---

## 1. 总原则

### 1.1 单一事实来源

同一类信息只在一个主文档里维护，其他文档只引用，不重复写第二份。

规则：

- 当前状态、已验证结果、下一步任务：以 `ICL_OpenHermes_TODO.md` 为准
- 文档结构、阅读顺序、参数复用规则：以 `README.md` 为准
- 理论设计与目标函数：以 `设计文档.md` 为准
- 稳定评测链路、命令协议、参数解释：以 `评测方案.md` 为准
- 标签图 / 选例 / baseline 映射运行手册：以 `MIG_标签图操作指南.md` 为准
- 历史实验、旧口径来源、设计演化：以 `历史实验与设计归档.md` 为准
- 新对话如何快速读文档：以 `SOP_新对话文档读取与防乱码.md` 为准

### 1.2 文档只保留“对未来有用”的信息

不要把文档写成聊天记录。

应该写入的内容：

- 新的稳定结论
- 新的可复现实验结果
- 新的稳定运行入口
- 新的固定口径
- 会影响后续决策的风险、限制、注意事项

不应该写入的内容：

- “今天试了几个参数，感觉一般”
- 没有落盘证据的猜测
- 一次性调试噪音
- 明显会过时、但没有历史追溯价值的细枝末节

### 1.3 优先更新现有文档，不轻易新增同类文档

只有当新内容属于一种全新的职责，且放进现有文档会破坏结构时，才新增文档。

如果只是：

- 新结果
- 新风险
- 新命令
- 新参数说明

优先更新现有对应文档。

## 2. 哪些进展该更新到哪里

下面是最重要的分流规则。

### 2.1 更新 `README.md`

只在以下情况更新：

- `docs/` 的文档结构发生变化
- 新增或删除了一个需要长期维护的文档
- 某份文档的职责边界发生变化
- 项目整体快照发生了“入口级别”的变化
- 参数复用规则需要新增一条通用约束

不要因为一次实验结果变化，就去改 `README.md`。

### 2.2 更新 `ICL_OpenHermes_TODO.md`

以下情况应更新：

- 当前项目快照发生变化
- 已完成能力新增
- 已验证结果新增或被更正
- 当前主要风险变化
- 下一步 TODO 优先级变化
- 某个原本未完成的事项已完成
- 某个固定口径已经稳定下来

更新要求：

- 更新“更新日期”
- 用明确数字，不写模糊描述
- 只保留当前最重要结果，不堆积旧会话历史

### 2.3 更新 `评测方案.md`

以下情况应更新：

- 新增稳定评测脚本或稳定评测链路
- 某个命令的推荐参数口径发生变化
- 评测产物目录规范变化
- 新增必须解释清楚的命令参数
- HumanEval / APPS 的评测协议发生变化

不要把一次具体实验的详细结果流水账写进这里。  
结果摘要写 `TODO`，历史运行过程写归档。

### 2.4 更新 `MIG_标签图操作指南.md`

以下情况应更新：

- 标签图构建方式变化
- query-aware 选例命令变化
- baseline 映射生成方式变化
- 新增或废弃某个关键参数
- 新增新的运行入口脚本

这里写“怎么跑”，不写“这次跑出来多少分”。

### 2.5 更新 `设计文档.md`

以下情况应更新：

- 目标函数改了
- 新增或删掉一个核心建模项
- 理论假设或变量定义变化
- 长度惩罚、冗余惩罚、难度项等核心口径发生理论层变化

不要把“脚本怎么调用”“这次跑了什么命令”写进理论文档。

### 2.6 更新 `历史实验与设计归档.md`

以下情况应更新：

- 某次实验具有长期追溯价值
- 一个旧口径被新口径替换，但仍需解释来源
- 某份局部文档被删除，需要保留历史背景
- 某次重要结论未来可能需要回头核对

适合放这里的内容：

- 带日期的实验摘要
- 旧 run name 和当时的运行上下文
- 已废弃口径的来源说明

不适合放这里的内容：

- 当前权威默认值
- 当前最重要 TODO

### 2.7 更新 `SOP_新对话文档读取与防乱码.md`

只在以下情况更新：

- 文档阅读顺序变化
- 新增必须先读的文档
- 读取命令、编码处理或检索方式发生变化

## 3. 常见进展类型与更新落点

### 3.1 跑出一组新的正式结果

至少检查：

- `ICL_OpenHermes_TODO.md`
- `历史实验与设计归档.md`

如果结果影响评测协议或结果模板，再检查：

- `评测方案.md`

### 3.2 修了一个脚本参数坑，避免下次误用

至少检查：

- 对应脚本所在文档
- `README.md` 中是否需要补通用参数复用规则

例如：

- prompt / eval 参数坑：优先改 `评测方案.md`
- 选例 / 图参数坑：优先改 `MIG_标签图操作指南.md`

### 3.3 固定了一条新的设计口径

至少检查：

- `ICL_OpenHermes_TODO.md`
- `设计文档.md`

如果它会影响命令使用方式，再检查：

- `评测方案.md`
- `MIG_标签图操作指南.md`

### 3.4 删除或合并了一份文档

必须检查：

- `README.md`
- `SOP_新对话文档读取与防乱码.md`

如果旧文档中还有追溯价值：

- 把必要内容转移到 `历史实验与设计归档.md`

### 3.5 新增一个长期维护的脚本入口

必须检查：

- `README.md`
- 对应运行手册文档
- `ICL_OpenHermes_TODO.md` 的“稳定产物 / 已完成能力”

## 4. 每次同步时的强制检查清单

在修改文档前，先回答下面五个问题：

1. 这条进展属于“当前状态 / 运行手册 / 理论设计 / 历史归档”中的哪一类？
2. 它有没有权威落点？如果有，是否只改那一处主文档？
3. 这条信息是稳定结论，还是临时调试噪音？
4. 有没有需要写清楚的精确数字、日期、文件路径、命令参数？
5. 有没有哪份文档会因此变成过期信息？

在修改完成后，再检查下面六件事：

1. `README.md` 中的文档职责是否仍然正确
2. `ICL_OpenHermes_TODO.md` 的“更新日期”是否需要更新
3. 命令示例里的路径、`run-name`、`k`、`max_tokens` 是否还是当前口径
4. 是否误把调试参数写成了默认参数
5. 是否把同一条信息写进了两个主文档
6. 是否有旧结论需要改成“历史归档”，而不是继续留在主文档

---

## 5. 持久化进展时必须写清楚的要素

### 5.1 结果类进展

必须尽量写清楚：

- 日期
- 数据集
- 方法
- 关键超参数
- 指标数值
- 样本数
- 产物目录或文件路径

坏写法：

- “效果更好了”

好写法：

- “`2026-03-30` 重跑 HumanEval `Similarity-ICL (k=5)`，`pass@1=0.9024 (148/164)`，结果目录为 `data/icl/eval_metrics/...`”

### 5.2 命令类进展

必须尽量写清楚：

- 命令对应哪个任务
- 哪些参数是当前推荐值
- 哪些参数只是示例，不能直接复用
- 哪些参数与机器环境有关

### 5.3 设计类进展

必须尽量写清楚：

- 旧口径是什么
- 新口径是什么
- 为什么变
- 哪些代码 / 评测 / 命令会受影响

---

## 6. 禁止事项

以下做法默认禁止：

- 在 `README.md` 里堆实验流水账
- 在 `设计文档.md` 里写长段命令
- 在 `评测方案.md` 里堆会话历史
- 在 `TODO` 里保留过多过期结果，导致当前重点被淹没
- 删除旧文档却不处理其剩余引用
- 把没有核实的结果写成既成事实
- 把示例命令里的调试参数、缓存路径、旧 run name 直接当默认值

---

## 7. 推荐同步顺序

当一次开发或实验结束后，推荐按下面顺序同步：

1. 先确认产物是否真的落盘
2. 先更新权威主文档
3. 再更新需要引用它的入口文档
4. 如果有历史价值，再补归档
5. 最后检查是否存在悬空引用或过期描述

---

## 8. 最小同步模板

如果这次进展需要落盘，但时间有限，至少做到：

1. 在 `ICL_OpenHermes_TODO.md` 更新：
   - 当前快照
   - 已验证结果或主要风险
   - 下一步 TODO

2. 在对应专项文档更新：
   - 命令变化写到 `评测方案.md` 或 `MIG_标签图操作指南.md`
   - 理论变化写到 `设计文档.md`

3. 如有历史追溯价值，再写到：
   - `历史实验与设计归档.md`

---

## 9. 一句话判断规则

如果你不确定某条内容该写到哪里，就先问自己：

- 这是“现在该怎么做”吗？
  - 写主文档
- 这是“为什么后来变成这样”的历史吗？
  - 写归档
- 这是“理论上为什么这么设计”吗？
  - 写设计文档
- 这是“命令该怎么跑、参数该怎么解释”吗？
  - 写运行手册或评测方案
