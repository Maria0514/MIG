# 轻量标签器重构方案

本文档只负责一件事：为当前 `MIG-ICL` 实验提供一套“足够稳定、足够简单、不喧宾夺主”的标签器重构方案。  
当前项目状态请看 [ICL_OpenHermes_TODO.md](./ICL_OpenHermes_TODO.md)，标签图与选例命令请看 [MIG_标签图操作指南.md](./MIG_%E6%A0%87%E7%AD%BE%E5%9B%BE%E6%93%8D%E4%BD%9C%E6%8C%87%E5%8D%97.md)。

---

## 1. 为什么要重构

当前仓库里的 `query_labels` 主要来自离线 `InsTagger`，已经能支撑标签图与选例流程跑通，但在 `HumanEval` 上暴露出三个问题：

1. 标签过泛
   - 例如 `program`、`python programming`、`function definition`。
   - 这类标签在候选池中的覆盖面过大，容易削弱 `MIG` 的区分能力。

2. 元标签污染
   - 例如 `documentation`、`example`、`example usage`、`code comment`、`code review`。
   - 这类标签更像题面写法或说明文风，而不是任务语义。

3. 候选池标签噪声较大
   - 存在长尾、别名不统一和明显脏标签。
   - 当标签本身不稳时，`MIG` 比 `Similarity` 更容易被带偏。

因此，当前要解决的问题不是“追求最强标签系统”，而是“把标签信号收敛到一个足够稳定的辅助模块”，让实验重点仍然回到 `MIG` 本身。

---

## 2. 设计原则

### 2.1 标签是辅助信号，不是主角

- 本项目的核心实验对象是 `MIG-ICL`，不是标签器。
- 标签器只需要做到：
  - 比当前 `InsTagger` 更稳
  - 更少元标签污染
  - 更适合代码任务检索

不追求：

- 单独做一套大型标签研究
- 设计过多维度
- 为每个领域都做专门 taxonomy

### 2.2 轻量、受控、可复现

新的标签器应满足：

- 使用一套短 prompt
- 使用统一模型批量打标
- 输出固定 JSON 结构
- 标签数量有限
- 标签空间可控
- 后处理规则简单明确

### 2.3 先服务当前 coding 实验

- 当前主要目标是 `HumanEval` 与 `APPS(test)`。
- 因此第一版标签器优先服务代码任务。
- 如果未来迁移到别的任务，再考虑在此基础上增加通用层，而不是第一版就追求全领域通用。

### 2.4 复杂度红线

- 参考论文《#InsTag: Instruction Tagging for Analyzing Supervised Fine-tuning of Large Language Models》（arXiv:2308.07074），原方法是 open-set fine-grained tagger，并统计到约 `6.6K` 个标签。
- 本项目的标签器不能比该方法更复杂；更现实的要求是：必须明显比它更简单。
- 因此当前方案明确不做：
  - 无上限、无约束的 open-set 标签扩张
  - 大规模 taxonomy
  - 多阶段打标
  - tagger 之后再接一层复杂选择器
  - 为每类候选池分别维护一套大而全标签体系
- 当前目标是：一轮推理、一个固定 JSON、最多 5 个标签、极少后处理，给 `MIG` 提供粗粒度辅助信号即可。

## 3. 当前正式建议方案（覆盖上一版三字段方案）

### 3.1 为什么要改

上一版 `topic / technique / format` 三字段方案，以及随后尝试过的固定小标签池方案，都有一个共同问题：它们都把太多结果敏感性转移到了“标签集合怎么定义”上。

典型问题是：

- 如果标签集合偏算法题，OpenHermes 中的大量应用型任务就会被硬套到错误标签上。
- 如果别的研究者要迁移到其他领域，就不得不重新定义一套标签池，复现成本较高。
- 一旦标签池设计得不好，最后测到的就不只是 `MIG`，而是“这套人工标签池定义得好不好”。

因此，当前正式建议不再采用固定标签池，而改成“轻约束 open-set”方案。

### 3.2 新方案：轻约束 open-set

新方案只保留一个正式输出字段：

```json
{"labels": []}
```

为提高模型输出稳定性，允许模型同时输出一个短解释字段，但该字段不进入正式标签图与 `MIG` 计算：

```json
{"labels": [], "explanation": "..."}
```

规则固定为：

- 每条样本最多输出 `5` 个标签。
- 标签为短语级语义标签，不追求完整 taxonomy。
- 标签统一使用小写下划线风格。
- `explanation` 只用于帮助模型稳定输出和人工排查，不作为正式特征。
- 最终只保留 `labels` 写入 `query_labels`；`explanation` 只放在原始记录中备查。

### 3.3 输出约束

推荐约束如下：

- `labels` 最多 `5` 个。
- 标签尽量短，建议 `1-3` 个词。
- 使用 `snake_case`，例如：`string_processing`、`api_service`。
- 不确定时宁可少打，不要凑满。
- 不输出元标签，例如：
  - `program`
  - `python_programming`
  - `documentation`
  - `example`
  - `code_style`
  - `code_review`
- 不输出解释性长句作为标签。

### 3.4 为什么保留 `explanation`

参考 `InsTag` 的经验，要求模型同时输出一个简短解释字段，往往能让标签决策更稳定。

但这里要明确边界：

- 我们保留 `explanation`，不是为了把标签器做复杂。
- `explanation` 只是生成时的辅助锚点，帮助模型说明“为什么选这些标签”。
- 下游正式流程只消费 `query_labels`，不把 `explanation` 引入 `MIG` 打分，也不把它变成另一套结构化特征。

因此，它更像是“帮助输出稳定的副产物”，而不是额外的实验对象。

### 3.5 Prompt 约束

推荐 Prompt 保持为一轮、短提示、固定输出：

```text
你是一个用于代码任务检索的轻量标签器。
请阅读任务描述，输出 JSON：
{"labels": [], "explanation": ""}

要求：
1. labels 最多 5 个。
2. 标签使用小写下划线，尽量短。
3. 标签应描述任务语义，而不是文风或元信息。
4. 不要输出 program、documentation、example、python_programming、code_style 等元标签。
5. explanation 用 1-2 句简短说明为什么选择这些标签。
6. 如果不确定，少选，不要凑满。
7. 只输出 JSON，不要解释 JSON 之外的内容，不要续写对话。
```

### 3.6 为什么这一版更合适

- 比 `InsTag` 轻得多：不做大规模开放标签挖掘，也不追求数千标签体系。
- 比固定标签池更通用：迁移到其他领域时不需要先重设计一套池子。
- 比完全开放自由生成更稳：仍然有明确输出格式、数量上限和 stoplist 约束。
- 更符合当前项目目标：标签只提供粗粒度辅助信号，不把实验主角从 `MIG` 挪到标签工程上。

### 3.7 模型选型建议

当前不再默认使用 `30B` 级模型做正式打标，但也不建议退到过弱模型。

建议口径：

- 默认首选：`/public/huggingface-models/Qwen/Qwen3-8B`
- 原因：当前方案已改为轻约束 open-set，但仍是结构化 JSON 输出任务；`8B` 在能力和成本之间更平衡，适合作为第一轮冒烟模型。
- 冒烟标准：先做 `20` 条小样本，检查空标签率、明显错标率、元标签率和标签长度分布。
- 若 `8B` 在这一方案下仍明显不稳，再上调到 `14B` 这类更强的中等模型，但不增加标签结构复杂度。

## 6. 输入预清洗建议

在送入标签器前，建议对 `HumanEval` / `APPS` / 候选池统一做轻量预处理。

### 6.1 HumanEval

建议尽量保留：

- 函数签名
- 核心任务描述
- 必要约束

建议弱化或移除：

- doctest 示例
- `Example:` 段落
- `Note:` 段落
- 纯说明性注释
- 与求解语义无关的格式文本

目的不是“重写题目”，而是减少模型被 `example/documentation` 风格词带偏。

### 6.2 OpenHermes 候选池

建议优先抽取：

- `dialogs[0].content` 中最能体现任务目标的用户请求

如文本特别长，可限制长度，并优先保留：

1. 任务目标
2. 输入输出要求
3. 关键约束

---

## 7. 后处理规则

后处理应保持简单，不要再引入复杂规则系统。

建议只保留下面几类操作：

### 7.1 合法性校验

- 非法标签直接丢弃
- 不在候选集合中的标签直接丢弃
- 空字段按空列表或默认值处理

### 7.2 去重

- 同一字段内标签去重

### 7.3 统一别名

如果后续发现必要，可仅保留极少数稳定别名映射，例如：

- `dp -> dynamic_programming`
- `binary search -> binary_search`
- `two pointers -> two_pointers`

### 7.4 Stoplist

对明显元标签使用固定 stoplist 过滤。

---

## 8. 与当前 MIG 实验的关系

### 8.1 目标

这次重构不是为了证明“新标签器绝对更强”，而是为了降低标签噪声，让下面的问题更可回答：

- 如果标签质量更稳定，`MIG` 是否能缩小与 `Similarity` 的差距
- `MIG` 到底是在吃到真实语义增益，还是被开放式标签噪声压制

### 8.2 预期收益

如果方案有效，最可能出现的变化是：

1. Query 标签更聚焦任务语义
2. Demo 检索更少跑偏到说明文风或泛 Python 任务
3. `MIG` 相比 `Similarity` 的差距缩小
4. 标签图和 IDF 权重更稳定

### 8.3 不应期待的事情

不应把本方案当作：

- 直接提升所有任务表现的万能方法
- 替代 `Similarity` 的唯一信号
- 一次性解决所有候选池错配问题

---

## 9. 推荐验证顺序

为了避免重构范围过大，建议按下面顺序进行：

1. 先对 `HumanEval` query 重打标签
2. 只抽取一小批与 `sim > mig` 差异最明显的 query 做人工抽查
3. 再对候选池做一小批重打标签验证
4. 如果局部效果更稳，再批量重打全量候选池
5. 最后重跑 `MIG / Similarity` 对比

---

## 10. 推荐部署方式（本地算力受限时）

如果本地算力不足，不建议为了打标单独在本地硬跑模型，也不建议第一步就维护常驻 API 服务。当前更推荐的落地方式是：

1. 本地准备数据与脚本
2. 上传到云服务器
3. 在云端离线批处理打标
4. 下载打标结果回本地
5. 继续使用本地既有 `MIG` 选例与评测链路

这样做的原因是：

- 工程复杂度最低
- 不需要额外维护在线服务
- 便于断点续跑与批量复核
- 不会打断当前仓库里“预标注数据 -> 选例 -> prompt -> infer -> eval”的主流程

### 10.1 第一阶段范围

第一阶段只建议重打 `HumanEval` query，不直接重打全量候选池，也不先展开 APPS 全量重打。

这样可以先回答最关键的问题：

- 轻量标签是否确实减少了 `HumanEval` 的过泛标签与元标签污染
- 在 `sim > mig` 的差异样本上，query 标签是否更贴近任务语义
- 在不扩大工程面的前提下，`MIG` 与 `Similarity` 的差距是否缩小

### 10.2 本地应准备的最小上传包

建议只上传打标必需内容：

- 轻量标签器说明文档
- 待打标源数据，例如 `data/icl/humaneval_eval.jsonl`
- 轻约束 open-set 的 JSON 输出格式（`labels + explanation`）
- 输入预清洗脚本
- 云端批量打标脚本
- 结果校验脚本

不建议把整个仓库一次性上传到云端，只为完成第一阶段 query 打标。

### 10.4.2 增量续跑口径

当前脚本已经支持断点续跑：

- 如果输出文件不存在：从头打标
- 如果输出文件已存在：先读取现有 JSONL，按 `_id / id / task_id / prompt hash` 跳过已完成样本，只继续剩余部分
- 运行时应关注：`existing_rows`、`skipped_existing`、`pending_rows`

对于新方案，正式输出文件名仍建议复用旧路径，但要在新产物第一次通过冒烟后再开始重建。因此当前只保留这条建议，不继续扩写旧结果：

- `/root/data/MIG/cloud_tagger_runs/openhermes_python_related.jsonl`

不要因为中断就更换正式输出文件名，否则后续会失去自动续跑的意义。

### 10.4.3 参数选择建议

当前参数建议不是追求单次最快，而是优先保证标签风格稳定：

- `batch_size`
  - 当前推荐值：`OpenHermes` 冒烟先用 `4`
  - 原因：`Qwen3-8B` 在单卡 `A800 80GB` 上可以承受这一批量，且当前 `20` 条冒烟已跑通
  - 若后续继续加大，只建议在同一批固定样本上先做对照，再决定是否统一升级

- `max_new_tokens`
  - 当前正式推荐值：`160`
  - 原因：当前 schema 输出很短，但历史上模型偶尔会回显 prompt 或输出多段 JSON；`160` 是保守但稳定的上限
  - 当前不建议为了提速单独改小，避免再次引入“同批数据口径不一致”

- `device`
  - 当前正式推荐值：`cuda`
  - 对应单卡 `A800 80GB`

- `model`
  - 当前新方案默认推荐值：`/public/huggingface-models/Qwen/Qwen3-8B`
  - 原因：新方案已改为轻约束 open-set，但仍有严格 JSON 约束与数量上限；`8B` 是当前已跑通的首个中等体量模型，若后续仍不稳，再上调到 `14B`，但不增加标签复杂度

- `local_files_only`
  - 当前正式推荐值：开启
  - 原因：当前直接加载 `/public` 预置模型，不再依赖线上拉取

- `disable_chat_template`
  - 当前 `Qwen3-8B` 冒烟推荐值：开启
  - 原因：不关闭时，模型容易输出 `assistant / <think>` 风格内容，导致无法稳定抽取 JSON；关闭后当前 `20` 条 OpenHermes 冒烟已恢复正常产出

脚本当前还会额外输出纯计时信息：

- `[timing] model_load_sec=...`
- `[progress] ... batch_elapsed_sec=... avg_batch_sec=...`
- `[timing] total_elapsed_sec=...`

### 10.4.4 预处理与校验命令

`OpenHermes` 预处理输入：

```bash
mkdir -p /root/data/MIG/tagger_inputs

/root/code/.venvs/cloud_tagger/bin/python - <<'PY'
import json
from pathlib import Path

src = Path('/root/data/MIG/openhermes_python_related.jsonl')
out = Path('/root/data/MIG/tagger_inputs/openhermes_python_related_for_tagger.jsonl')

with src.open('r', encoding='utf-8') as fin, out.open('w', encoding='utf-8') as fout:
    for line in fin:
        if not line.strip():
            continue
        row = json.loads(line)
        prompt = ''
        for turn in row.get('dialogs', []):
            if turn.get('role') == 'user':
                prompt = turn.get('content', '')
                break
        row['prompt'] = prompt
        fout.write(json.dumps(row, ensure_ascii=False) + '\n')

print(out)
PY
```

### 10.5 云端回传产物

云端回传结果时，应至少保留下面几类信息：

- 与原 query 对齐的主结果 JSONL
- `query_labels`
- `query_tags_raw`
- `query_tagger_raw_text`
- 空标签率、非法标签率、平均标签数等统计摘要

其中 `query_labels` 仍应作为当前本地流程的主消费字段。新方案建议云端输出 `labels + explanation`，但回传给本地流程时只把 `labels` 写成稳定的 `query_labels`；`explanation` 仅保留在原始记录中，避免影响现有 `utils/select_icl_examples.py` 和 `mig/icl_selector.py`。

### 10.6 推荐操作顺序

建议按下面顺序执行：

1. 本地先抽 `20-50` 条 `HumanEval` 做冒烟打标
2. 人工检查是否仍有明显元标签、空标签和错误格式
3. 通过后再在云端打完整 `HumanEval`
4. 本地回收结果，并在 `sim > mig` 差异样本上做人工抽查
5. 如果结论成立，再扩到 APPS query 或候选池小样本

### 10.7 当前不推荐的方式

当前阶段不推荐：

1. 为打标先搭建长期在线推理服务
2. 一开始就重打全量 OpenHermes 候选池
3. 在本地和云端并行维护两套不一致的 prompt / 标签集合
4. 让云端输出格式和本地 `query_labels` 消费口径脱节
5. 在同一批正式标签数据里混用 `transformers` 与 `vLLM` 结果

## 11. 最小实施版本

如果时间有限，至少做下面四件事：

1. 定义固定的 JSON 输出约束（不定义固定标签池）
2. 写一个短 prompt，强制输出 JSON
3. 保持后处理最小化，只做格式归一与去重
4. 先重打 `HumanEval` query，而不是一开始就重打全量池

只要这四步做完，就已经比当前开放式标签更容易分析，也更符合“标签服务于 MIG 实验”的目标。

---

## 12. 暂不做的事情

当前版本明确不做：

1. 面向所有领域的统一大 taxonomy
2. 复杂多层标签图谱
3. 独立训练一个新标签模型
4. 过多字段的结构化标注
5. 把标签器本身当成主实验对象

---

## 13. 一句话结论

当前最合适的方向不是继续追求更复杂的开放式标签器，而是用一个统一的小型 instruct 模型，配合短 prompt、固定 JSON 约束和少量后处理，产出一套足够干净、足够受控的代码任务标签，让 `MIG` 的实验重点重新回到选例算法本身。
